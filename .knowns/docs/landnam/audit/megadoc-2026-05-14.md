## 4. State Management & Save Strategy for Next.js PWA

### 4.1 What `user://` Maps to in Web Export

When Godot 4.x is exported to Web (HTML5), `user://` maps to the browser's **IndexedDB** under the application's origin. The custom user dir name "Landnám" (set in `project.godot`) becomes the storage key prefix.

**IndexedDB properties and risks:**
- Per-device, per-browser, per-origin only
- Cleared automatically under browser storage pressure (especially on iOS Safari)
- Wiped in private/incognito mode — every session is a new player
- Not accessible across browsers or devices (player on Chrome can't resume a Firefox session)
- No server-side backup unless explicitly synced

**Current mitigation:** AppController partially mirrors XP/level to `localStorage` (lines 698–709). But Francs, missions, inventory, mission logs, subcontractor state, and construction state are IndexedDB-only. If IndexedDB is cleared, the player loses everything except XP level.

### 4.2 The Correct Layered Architecture

The architecture should follow this three-layer model:

**Layer 1: In-Memory Godot Resources (Instant feedback)**
- `PlayerProfile` resource (already implemented at `Scripts/Resources/PlayerProfile.gd`) holds the canonical in-session state
- All UI reads from `PlayerProfile` via `PlayerManager.get_snapshot()`
- Updates are applied optimistically: UI responds immediately, no wait for network
- Never persist `PlayerProfile` to disk as the source of truth — it's a working copy

**Layer 2: Godot → Next.js via WebEventBridge (Event stream)**
- Every meaningful state change emits via `WebEventBridge.emit()` (already wired in `SyncBridge.gd`)
- Events include: `franc_balance_changed`, `experience_changed`, `player_state_changed`, `mission_completed`
- The Next.js PWA shell receives these via `window.addEventListener("message", ...)` filtering `source === "landnam"`
- Next.js is the **single authority** for Supabase writes — Godot never calls Supabase directly for player state (contrast: current `SupabaseClient.gd` makes classification calls from GDScript, which should move to the PWA shell)

**Layer 3: Next.js → Godot reconciliation (Source of truth push)**
- After every Supabase write, Next.js pushes the server-confirmed state back to Godot via `postMessage` with `source: "landnam-pwa"`
- `SyncBridge._handle_pwa_message` (line 29) already implements the listener
- `_on_pwa_state_received` (line 63) applies franc_balance, xp, and counter — **this should be extended to cover mission state**
- On session resume (app open), Next.js fetches from Supabase and pushes the full player snapshot to Godot before gameplay begins

### 4.3 What NOT to Use

| Pattern | Why to Avoid |
|---------|-------------|
| `user://` as primary persistence | IndexedDB cleared by browser; not cross-device |
| Direct `SupabaseClient` calls from GDScript | Anon key exposed in binary; RLS blocks writes; no retry/queue |
| `localStorage` as primary state store | Only 5–10 MB quota; synchronous blocking; not relational |
| Multiple `.cfg`/`.json` files for same domain | No transaction safety; race conditions on rapid save |
| Polling `RocketsManager.load_state()` on every frame | Disk read per call; no caching; performance degradation |

### 4.4 Offline / Optimistic UI Pattern

1. Player action triggers state change in Godot
2. Godot updates `PlayerProfile` in-memory immediately (optimistic)
3. Godot emits event to Next.js via `WebEventBridge`
4. Next.js queues the write and applies locally (React state)
5. If online: Next.js writes to Supabase, gets confirmation, pushes back confirmed state
6. If offline: Next.js holds the queue, applies locally, syncs when reconnected
7. Godot does NOT retry — it trusts the Next.js layer to eventually confirm

`user://` files should be treated as an offline write-ahead log only — not the source of truth. If Supabase confirms a different state, the confirmed state wins.

### 4.5 Session Resume Flow

On app open:
1. Next.js auth layer restores session from AsyncStorage (`AuthContext.tsx`)
2. Next.js fetches player state from Supabase
3. Next.js embeds the full state in the initial `postMessage` to Godot iframe before gameplay starts (or within 500ms of `app_ready` event)
4. `SyncBridge._on_pwa_state_received` applies the full snapshot
5. Godot renders from the server-confirmed state

Currently, `app_ready` is emitted in `AppController._ready()` (line 75) but `_sync_experience_from_web_storage` (line 69) only reads localStorage — not Supabase. The PWA must push Supabase state into Godot on every session start, not just on change.

## 5. Full Game Cycle (As Understood from Codebase)

### 5.1 App Launch / Auth

The Next.js PWA (`AuthContext.tsx`) checks AsyncStorage for a saved Supabase session. If no session: `LoginScreen.tsx` is shown with email/password, anonymous login, or guest options. If a session exists, it is restored automatically and the game screen loads. The Godot iframe is embedded in the Next.js game screen behind a CanvasLayer.

Godot's `_ready()` fires in `AppController.gd`. It:
1. Loads franc balance from `user://franc_balance.cfg`
2. Loads experience from `user://experience.cfg`
3. Reconciles experience level with mission stage (overriding XP accumulation)
4. Loads citizen science dialogue preference
5. Spawns MissionProgressTracker, TutorialController, FeedbackBeacon as root-level children
6. Emits `app_ready` event to Next.js via WebEventBridge

If the PWA has Supabase state to push, it should do so immediately after receiving `app_ready`.

### 5.2 Earth Base Scene

Main scene: `/Users/scroobz/Navigation/Landnam/scene/Scenes/Earth/earth_base_1.tscn`

The player sees a 2D backdrop with:
- Background layer: sprites, star field, sky map, cloud drift, night filter events (all live in `Environment/` scripts)
- Structures layer: SatelliteStation (Scanner), Launchpad, and optionally a ControlStation
- UI layer: nav buttons (Back, Forward, Menu, Market, SpaceMap, Build, NewMission), Planet Hunters wordmark, ProgressionCards

The ProgressionCards (VBoxContainer in UILayer) show contextual cards:
- `ActiveMissionCard` — visible when a mission is in flight
- `ControlStationCard` — build prompt visible pre-M2
- Additional cards populated by `EarthBaseProgressionCards.gd`

The player can open panels via the nav buttons, click structures directly, or interact with progression cards. The weather engine (`EarthWeatherEngine.gd`) runs ambient environment events.

### 5.3 Mission Creation Flow (LaunchWizard / Fabrication Bay)

Triggered by "New Mission" button. The `LaunchWizard.tscn` is instantiated (or already in the scene). The wizard walks through:

1. **Contractor selection**: The player picks from available contractors (3–10 depending on level). `SubcontractorManager.get_roster(level)` returns the list. Contractor cooldowns (30-min after 2 consecutive uses) are enforced.
2. **Target selection**: The LaunchWizard shows available targets depending on mission stage. M1: predefined Eros. M2: Active Asteroid fallbacks. M3: TESS planet candidates. Free Ops: procedurally available targets from `RocketsManager.get_available_targets()`.
3. **Fabrication Bay (rocket selection)**: The programmatically-built module rail (LaunchWizard.gd lines 793–982) shows available rockets. SR1 is always available; SR2/SR3 unlock at level 2/3.
4. **Confirmation**: LaunchWizardConfirmFactCard.tscn, LaunchWizardConfirmManifestCard.tscn show the mission summary.
5. **Launch**: `award_launch_experience()` adds 5 XP. `RocketsManager` records the mission. Scene transitions to `rocket_ascent.tscn`.

The mission struct is stored in `rockets_state.json` under `missions[]` with `status: "in_flight"`, target details, contractor ID, launch timestamp, and cargo manifest.

### 5.4 Rocket in Flight / Mission Active State

The `rocket_ascent.tscn` (`Scripts/Transitions/RocketAscent.gd`) plays the launch animation. After the ascent, the game routes to the mining minigame.

Mining is `MiningMinigame.gd` (a thin wrapper that delegates to `SidescrollMining.tscn`). The minigame:
- Generates terrain procedurally via `MiningTerrainGenerator.gd`
- Tracks mineral regions and allows player to fire a mining beam
- Up to 3 drones (`MAX_DRONES = 3`) can be deployed for subsurface extraction
- Fuel drains at `FUEL_DRAIN_RATE = 2.0` per second; heat accumulates at `HEAT_GAIN_RATE = 25.0`, cools at `HEAT_COOL_RATE = 18.0`
- Session duration: 90 seconds (asteroid) or 180 seconds (planet)
- On completion (or fuel depletion), `mining_completed` signal fires with collected minerals dictionary

Mission state during flight is tracked via `RocketsMissionProgress`. The `OutboundPreviewTransition` and `ReturnPreviewTransition` scenes (`Scenes/Transitions/`) show animated previews of the rocket journey.

### 5.5 Mission Return / Debrief

When the player returns, `mission_debrief_v2.tscn` loads (`Scripts/Earth/MissionDebriefV2.gd`). The debrief:
1. Reads the returned mission from `RocketsManager.get_returned_mission()`
2. Calculates payout: base mineral value × contractor route multiplier (1.2× for contractor missions) × affinity bonus (0.5% per affinity point, capped at 25%) × order fulfillment bonus (capped at 15%) × discovery bonus (1.1× if candidate visited)
3. Runs loan repayment: `AppController.repay_loan_from_payout(payout)` deducts from payout if a loan is outstanding
4. Awards XP: `XP_BY_MISSION_STAGE[stage]` (M1=80, M2=120, M3=160, M4=200) or `XP_FREE_OPS=100` for free ops
5. Adds minerals to inventory via `MiningInventory`
6. Records the mission in `MissionLogManager`
7. Awards subcontractor reputation via `SubcontractorManager.record_mission_completion()`
8. Calls `AppController.add_franc_balance()` with the payout
9. Emits `player_state_snapshot_updated` which cascades through PlayerManager → EventBus → SyncBridge → WebEventBridge → Next.js

The debrief has two phases: "reward" (sell options) and a post-debrief screen showing next mission options. M3 debrief triggers the Free Ops handoff dialogue (task `task-42m16e` is done).

### 5.6 Economy (Francs, Loans)

- **Starting balance:** 10B Francs (AppController line 16) — almost certainly wrong for production | No, this is intended. It allows the user a starting balance with some margin for error.
- **Earn:** Mission payouts (contractor = 120% base, open market = 80% base), discovery bonuses

- **Market:** Full market pricing visible at Level 5 only. Pre-L5 players rely on contractor quotes as the sole pricing signal. | Ignore this for now
- **Contractor bonus:** `ORBIT_SALE_MULTIPLIER := 0.8`, `EARTH_SALE_MULTIPLIER := 1.0`, `PURCHASE_MARKUP := 1.15` in `SubcontractorManager.gd`

### 5.7 XP / Leveling System

XP is managed entirely in `AppController.add_experience()` (line 556). The curve is `floor(100 * 1.5^(level-1))`:
- L1→L2: 100 XP
- L2→L3: 150 XP
- L3→L4: 225 XP
- L4→L5: 337 XP

Level-up triggers `_unlock_rockets_for_level()` and `_show_level_up_notification()`. The `LevelUpNotification.tscn` is instantiated as a child of AppController itself (line 783–785) — a UI node as a child of an autoload, which is unorthodox and may cause z-order issues.

**Critical bug:** `_reconcile_experience_level_with_mission_stage()` (line 619) **overwrites the level with the mission stage on every load**, clamped to 1–4. This means a player who completes M3 and earns enough XP to reach level 4 will have their level reset to 3 (stage=3) on next session. XP accumulation between mission stages is effectively discarded.

XP sources:
- Mission debrief: 80–200 XP per mission (from `MissionDebriefV2.gd` line 34)
- Launch: 5 XP (AppController line 45 — `XP_AWARD_LAUNCH`)
- Scan: 2 XP (AppController line 46 — `XP_AWARD_SCAN`)

### 5.8 Tutorial Flow

Despite task `task-5w8lx7` being marked done, the tutorial system is fully present:
- `TutorialController.gd` — manages `record_action`, `has_seen_tutorial_action`, `replay_current_mission`, `skip_all`
- `TutorialPersistence.gd` — saves seen actions to disk
- `TutorialCatalog.gd` — defines tutorial steps
- `TutorialCoachOverlay.tscn` — the coach UI (instantiated as a root-level node by AppController line 92–95)
- `TutorialCoachTargeting.gd` — highlights specific UI elements

The tutorial renders in the `TutorialLayoutZone.reserved_rect()` (right-side rail per the spec). AppController manages suspension via `_set_tutorial_overlay_suspended()` (line 347). Tutorial actions are recorded via `AppController.record_tutorial_action()` and queued if the controller isn't ready (`_pending_tutorial_actions` array at line 58).

### 5.9 Mining Minigame

Two-level structure:
1. `MiningMinigame.gd` — thin compatibility wrapper; delegates to `SidescrollMining.tscn`
2. `SidescrollMining.gd` — the actual implementation (large, ~800+ lines)

The sidescroll miner uses a `GuideStep` enum (INTRO → MINE_SURFACE_IRON → MINE_SURFACE_NICKEL → EXPLAIN_SUBSURFACE → DEPLOY_DRONE → COMPLETE) to sequence the tutorial steps within the minigame. The terrain loops continuously (hence `_terrain_loop_container`). Minerals are distributed in `_mineral_regions` populated by `MiningTerrainGenerator.gd`.

Rooms on the rocket are shown in a side panel via `MiningRoomRow.tscn` templates. The drone mechanic deploys probes to extract subsurface minerals.

Post-mining, `mining_completed(minerals, score)` signal fires. The caller (`LaunchpadScene.gd` or the transition flow) stores results in `AppController.set_last_mining_result()`.

### 5.10 Scan / Satellite Station

`SatelliteStation.gd` manages build gating. `SatelliteStationPanel.gd` (the main UI) has four sub-controllers:
- `SatelliteStationPanelData` — fetches anomalies from Supabase via `SupabaseClient.get_instance()`
- `SatelliteStationPanelList` — renders the list of discovered candidates
- `SatelliteStationPanelDetail` — shows a candidate's full detail view
- `SatelliteStationPanelLoading` — loading state

Scanning awards 2 XP per scan. A soft cooldown (`SCANNER_SOFT_COOLDOWN_SECONDS := 120`, 2 minutes) prevents immediate rescanning. The scanner unlocks after 3 completed missions (`SCANNER_UNLOCK_COMPLETED_MISSIONS := 3`).

Classification: the player annotates a TESS lightcurve (drawing on a canvas), then submits `planet` or `not_planet`. The submission goes to Supabase via `AsteroidDetailView.gd` line 444 → `SupabaseClient.get_instance()`. This fails in production with 401 (task `t8fm49`).

### 5.11 Control Station

`ControlStation.gd` opens `ControlStationPanel.tscn` on interact. The panel shows:
- Active missions (via `ControlStationActiveMissionCard.tscn` templates)
- Mission queue
- Mineral inventory chips (`ControlStationMineralChip.tscn`)
- Log lines (`ControlStationLogLine.tscn`)
- Story cards (`ControlStationStoryCard.tscn`)

The Control Station is unlocked at M2 (costs 500M F). Clicking it before it's built shows a build prompt. After build, it is the primary mission management dashboard.

A known issue: `ControlStation.gd` (lines 17–34) uses a two-step UIManager discovery pattern (first `get_first_node_in_group`, then iterating children) that will fail silently if neither search finds the UIManager. No error is surfaced to the player.
