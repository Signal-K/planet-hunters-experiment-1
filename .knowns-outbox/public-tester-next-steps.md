# Public Tester Next Steps (M1 polish session)

## Update: PostHog analytics + survey-based feedback (follow-up)

Added at Liam's request, after the initial M1 polish pass below:

- `web/lib/analytics.ts`: thin PostHog wrapper. `initAnalytics()` calls
  `posthog.init` only if `NEXT_PUBLIC_POSTHOG_KEY` is set (reads
  `NEXT_PUBLIC_POSTHOG_HOST` for self-hosted instances, defaults to
  `https://us.i.posthog.com`). Everything is a safe no-op until that
  env var is configured. Also exports `track(event, props)` and helpers
  for surfacing/recording PostHog "external_survey" surveys
  (`getFeedbackSurvey`, `trackSurveyShown/Sent/Dismissed`,
  `surveyResponseKey`).
- `web/components/game/SurveyPrompt.tsx` (new): renders a matching
  `external_survey` (max 2 questions — rating / single_choice /
  multiple_choice / open) with in-game styling, and reports
  `survey shown` / `survey sent` / `survey dismissed` events in the
  shape PostHog expects (`$survey_id`, `$survey_name`,
  `$survey_response[_N]`, `$survey_completed`).
- `web/components/game/FeedbackButton.tsx`: now fires `feedback_opened`
  on open, tries to surface a matching PostHog external survey via
  `SurveyPrompt`, and otherwise falls back to the existing free-text
  textarea. If analytics is configured, free text can be submitted
  directly as a `feedback_submitted` PostHog event (in addition to the
  existing copy/email fallback, which always remains available).
- Funnel events added via `track()` at: `intro_begin_operations`
  (first hydration while still in the M1 tutorial),
  `launchpad_built` (`web/components/game/GameApp.tsx`'s `onPlaced`),
  `mission_selected`, `target_selected`, `assembly_confirm_launch`,
  `mining_order_completed`, `reward_collected` (all in
  `web/game-context.tsx`), `transit_arrived` + `mining_started`
  (`GameApp.tsx`'s transit `onArrive`), and `debrief_resolved`
  (`DebriefScreen.tsx`'s "Resolve Cargo" button). Only screen names,
  mission/target IDs, counts, and totals are sent — no PII.
- `web/.env.example` (new, force-added past `.env*` in `.gitignore`):
  documents `NEXT_PUBLIC_SHARED_PB_URL`, `NEXT_PUBLIC_LANDNAM_PB_URL`,
  `NEXT_PUBLIC_POSTHOG_KEY`, `NEXT_PUBLIC_POSTHOG_HOST` as placeholders.
- `npm install posthog-js` (added to `web/package.json` /
  `package-lock.json`).
- Verified: `npm run typecheck`, `npm run test:unit`, `npm run build`
  all pass; `next dev` serves `/game` (200 OK).

**Still needed to go live**: set `NEXT_PUBLIC_POSTHOG_KEY` (and
`NEXT_PUBLIC_POSTHOG_HOST` if self-hosted) in the deploy environment.
Until then all of the above is inert. Once configured, the existing
`scripts/posthog/*.json` survey definitions (already `type:

`SurveyPrompt` as long as their targeting conditions match.

## What changed this session

- `web/components/game/screens/BuildPlaceScreen.tsx`: the plot-picker
  row and guideline in the "place" phase were anchored with hardcoded
  `top` pixel values tuned for an 874px-tall canvas. On shorter
  viewports (`100dvh - 32px < ~750px`, common with mobile browser
  chrome) the plot buttons could render underneath or past the
  Confirm bar. Re-anchored both elements with `bottom` offsets so they
  always sit above the sticky Confirm bar regardless of canvas height.
- `web/components/game/screens/MiningScreen.tsx` +
  `web/app/globals.css`: ore nodes that match an unfilled contract
  mineral now get a stronger pulsing ring (`.ore-node--ordered`) and
  the order rows show a checkmark once a mineral quota is met. This
  gives players a clear "mine this one" signal instead of clicking
  randomly.
- `web/components/game/FeedbackButton.tsx` (new) wired into
  `GameApp.tsx`: a small persistent icon button (bottom-left of the
  canvas) opens a modal with a textarea, "Copy Text", and an
  `Email Feedback` (`mailto:`) action. The modal explicitly says this
  build doesn't submit feedback automatically. This is a stop-gap —
  see "Feedback pipeline" below for the real fix.

Known minor issue: the new feedback button (bottom-left, 32px) can
slightly overlap the bottom-left corner of the Mining screen's
"Contract Order" panel on very short viewports. Cosmetic only, does
not block the Return Home button.

## Remaining before public-tester readiness

1. **Feedback pipeline**: decide whether feedback should post to the
   shared PocketBase (`http://localhost:8090`) as a `feedback`
   collection, or to PostHog surveys, or stay email/copy-only. The
   current `FeedbackButton` is a safe placeholder but won't produce
   structured data for analysis.
2. **Analytics/funnel events**: `web/` has no analytics helper
   (`lib/analytics.ts` or similar) and no PostHog SDK dependency. The
   funnel events requested in the task brief
   (`intro_begin_operations`, `launchpad_built`, `mission_selected`,
   etc.) cannot be added as "safe no-ops" without first deciding where
   they should go (PostHog? PocketBase? console-only stub?). Recommend
   a small follow-up task: add `lib/analytics.ts` with a `track(event,
   props)` function that no-ops if no provider is configured, then
   call it from `game-context.tsx` at the funnel transition points
   (`onPickMission`, `onPickTarget`, `onLaunch`, `onMiningDone`,
   `onDebriefDone`, mission-board "build gate" resolution, etc.).
3. **Viewport coverage**: `BuildPlaceScreen` was the only screen
   audited for the "fixed-pixel-positions assume 874px canvas" pattern
   this session. Other screens (`MissionBoardScreen`,
   `ClassifyLightcurveScreen`, `TransitScreen`) use similar absolute
   positioning and should get the same short-viewport audit.
4. **Tutorial coach overlap**: `TutorialCoach.tsx`'s `compactBottom`
   logic (bottom-anchored pill at `bottom: 110`) was reviewed for
   collisions with sticky bottom bars (Assembly's `.sticky-actions`,
   Mining's `.mining-order`). Step 4 (Assembly) uses the `manual`
   variant which is top-anchored and does not collide. No live
   collision found in the M1 step set, but this logic is fragile if
   new steps are added with `spot.y + spot.h/2 < 437` on screens that
   have a sticky bottom action bar — worth a comment/guard if extended.
5. **Browser testing**: not performed this session (no headed browser
   available). `npm run typecheck`, `npm run test:unit`, and
   `npm run build` all pass; `next dev` starts and serves `/game`
   (200 OK), but the M1 flow itself was not clicked through.

## What would make users come back

- A persistent sense of progression beyond the M1 authored missions —
  `FREE OPERATIONS` (post-M1 unlock) is referenced in
  `lib/data.ts`/`UnlockPopup.tsx` but the Market screen is explicitly
  "buy/sell not yet implemented" per `CLAUDE.md`. Without a sink for
  Francs beyond cosmetics, repeat sessions feel pointless once M1 is
  done.
- Visible citizen-science feedback loop: after `/classify`, players
  currently get no sense of whether their classification mattered
  (consensus, "X other players agreed", etc.). Even a simple
  "your classification has been recorded — N pending review" helps
  retention and trust in the science framing.

## What would improve scientific output

- Make the link between mining targets and real TESS data more
  visible in the Atlas/Target picker — right now `TargetPickerScreen`
  shows orbit/difficulty but not which bodies have pending
  classification work.
- Surface `mission.requiresClassification` mining targets more often
  post-M1 so classification isn't a one-time M2 step.

## Asset/sprite work with the most perceived-quality impact

- `BuildPlaceScreen` and `HubScreen` plots are CSS/SVG ellipses and
  procedural icons (`StructureIcon`) — real placed-structure sprites
  (matching the `Building` SVGs but as illustrated art) would be the
  single biggest visual upgrade for the first-session loop, since the
  Hub and Build screens are seen first and most often.
- `MiningScreen`'s ore nodes are plain colored circles with a symbol —
  small mineral-specific sprite icons (matching `MineralChip`'s
  per-mineral colors already defined in `lib/data.ts`) would make the
  new "ordered" highlight read more clearly.
