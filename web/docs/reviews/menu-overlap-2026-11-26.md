# Menu and navigation overlap review — 26 November 2026

Scope: source review of the web game router, base dock and menu, mission board and planner, launchpad, debrief, market, data hub, probe and community-research navigation. This is not a visual walkthrough of every state or a review of iOS. Conditional and progress-dependent states need a player walkthrough before removing controls.

## Confirmed repetition

1. **Debrief: next-activity instructions.** The generic “Choose your next activity” card repeated the persistent “Choose next flight” and “return to Base” actions. Removed the generic sentence; mission-specific story and probe guidance remains. The “More activities” disclosure remains when it contains other destinations. Source: `web/components/game/screens/DebriefScreen.tsx`.
2. **Probe debrief: two scanner actions.** `debriefExits` includes “Open probe scanner” while the primary dock button already completes the flight and opens that scanner. The duplicate was removed from More activities; the primary button remains. Source: `web/lib/debrief-exits.ts`, `web/components/game/screens/DebriefScreen.tsx`.
3. **Empty launchpad: two mission selectors at once.** `RocketBuilderScene` renders the persistent “Select mission” control and, when the pad is idle, a prominent “Choose a mission” control. Both call `onChooseMission`. The latter is a strong contextual empty-state invitation; the former is an intentionally persistent route (see its CSS note). Test discoverability before consolidating them, rather than deleting either blindly. Source: `web/components/game/screens/RocketBuilderScene.tsx`.

## Overlapping journeys worth simplifying

4. **Free run and Plan flight** both start self-directed work. The Mission Board has a Free run tab that chooses a site and an existing run, plus a Plan flight button that opens the separate planner, where players choose work, destination and amount. They do not currently produce identical mission configurations; presenting them as two unexplained ways to do your own flight makes the distinction hard to discover. Candidate: one map-first entry with quick-start and customize paths, retaining existing mission IDs and saves. Source: `web/components/game/MissionBoard.tsx`, `web/components/game/screens/MissionPlannerScreen.tsx`, `web/components/game/MissionSetupRoutes.tsx`.
5. **Probe data to mission:** a probe result offers a free run, a mineral plan, and contract filtering through three separate handlers. These lead to different mission systems, so they are not redundant buttons, but they fragment a single “do something at this location” intention. Candidate: carry the selected body and resource into one location action surface and offer the three outcomes there. Source: `web/components/game/GameScreenRouter.tsx` (`probe-scan`), `web/components/game/screens/ProbeScanScreen.tsx`.
6. **Research is spread across differently purposed destinations.** Data hub handles instruments, feeds and probe data; Community research handles shared activities and rewards; the Market research tab converts fragments and unlocks technology. These are not equivalent screens, but the same word can lead players to expect the same place. Candidate: distinguish “Data”, “Community projects” and “Technology”, and cross-link them where the player's next action requires it. Sources: `web/components/game/screens/InstrumentHubScreen.tsx`, `CommunityResearchScreen.tsx`, `MarketScreen.tsx`.
7. **Mission history has multiple entry points:** Mission Board’s Mission log and the base agency landmark can both lead to `mission-history`. These are shortcuts to the same screen, not duplicate components. Keep both unless testing shows navigation clutter. Sources: `web/components/game/MissionSetupRoutes.tsx`, `web/components/game/screens/HubScreen.tsx`.
8. **Base shortcuts overlap with the Command menu.** The dock, world buildings, sky craft and status chips can open places also listed in the base menu (for example Marketplace, Data hub and Community research). Contextual shortcuts are useful; the risk is inconsistent naming or excessive simultaneous calls to action, not duplicate underlying screens. Source: `web/components/game/screens/HubScreen.tsx`, `web/components/game/hub/BaseDock.tsx`, `BaseMenuSheet.tsx`.

## Component consolidation candidates

- `MissionBoard`, `CommunityResearchScreen` and `ProbeScanScreen` use related board/rail styling and list-detail interactions, while representing different data and actions. A shared shell could reduce UI drift; merging the screens would lose context. Inspect keyboard and mobile behavior first.
- `MissionPlannerScreen` and the Mission Board Free run view each select destination and work but have different plan semantics. Share the location picker and labels once their models are mapped, not the mission state itself.
- Base dock and base menu both express destinations, but they serve persistent navigation and a broader destination list respectively. A shared typed destination registry may prevent label/route drift while preserving both entry points.

Recommended next slice: use the selected location as the common entry point for free runs, custom plans and available contracts; then run a compact, real-device navigation review across early, mid and returning-player states. Keep existing saves and links compatible.
