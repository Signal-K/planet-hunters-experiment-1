# Experimental solar terrain connection

The optional web connection samples a versioned Takeon Go solar landing patch and converts its elevation to the DEM used by the playable Takeon field. The landing scene's generated orbital globe, its landing patch, and fresh tutorial delivery fields use the same body, seed, style version and coordinates. The globe samples a broad hemisphere, while the field uses a local elevation grid. The globe is shown only when its centre sample matches the landing patch. The orbital globe and landing preview use the same biome colour mapping and landing samples. The landing preview draws an angled relief mesh and deterministic rocks from that patch; it is a visual scene, not the playable rover field.

The solar-system map's generated planet icons also use this WASM, even when the descent preview is disabled. The files are not committed: another checkout or deployment must build them before starting the web app. Use Takeon's `codex/kes-551-procedural-locations` branch at commit `d079e94` or a later compatible revision, and the Go version specified in its `go/go.mod`:

```sh
cd web
npm run sync:solar -- /path/to/takeon
NEXT_PUBLIC_TAKEON_SOLAR_PREVIEW=1 npm run dev
```

The path can be omitted when Takeon is a sibling checkout named `takeon`, or supplied via `TAKEON_GO_REPO`. If the Go toolchain is not on `PATH`, prepend its bin directory. Restart the web server after changing the preview flag. Without the assets the map falls back to plain icons; enabling the flag without matching assets cannot provide the generated descent or a selected-site rover field.

The WASM and its matching shim are ignored build output and must be provisioned for each deployment. If loading fails, the existing field remains available. Saved rover missions retain their existing generator: this experiment only applies to read-only fields and seeded, ephemeral tutorial fields. The existing illustrated globe is used if generation fails. Persistent fields are not connected; the mining preview uses the selected site’s biome colour as described below. The generated globe and field load asynchronously. This is not yet a complete orbit-to-surface connection.


For a stationary visual review, open `/game/stage/solar-visual` in the enabled development build. Choose a destination and use the percentage buttons to hold the real landing scene at points in the descent. The fixture does not change mission progress. Generated terrain needs the preview flag and matching Go assets above; check the browser console if the old view appears.

The visual fixture includes an observed-imagery slider for bodies with bundled global maps: Moon, Mars, Earth, Mercury, Venus, Jupiter, Saturn and Neptune. It blends the same registered image into both preview views. This changes colour only: the terrain and surface rocks are still procedural, and the slider is not a 1:1 reconstruction. Moon and Mars also have elevation datasets, but this control does not yet display unexaggerated measured elevation. The other six have imagery without measured elevation. Gas-giant maps show cloud tops, not terrain; the existing landing sampler rejects gas-giant landings. Destinations without imagery show the coverage gap rather than presenting invented data as observed. Data provenance and native resolution are documented in Takeon's `docs/solar-biomes.md` and `go/data/lunar/README.md`. The slider does not change world generation, player preferences, or saved mission state.

The Go bridge also exposes a versioned `solarOrbit` patch that works for landable bodies and gas giants, without permitting a gas landing. The visual fixture shows Jupiter as an orbit-only view, with generated cloud bands and an optional observed cloud image; Uranus has no bundled observed image. The fixture is a generator review, not a new gameplay mission route. Ceres and Lutetia now have deterministic stylised profiles, so all destinations in the current web target catalog have a generator profile. These additions do not alter version-1 sampling for previously supported bodies.

Mission selection and launch share a destination capability rule: gas giants accept orbital payloads, while mining, delivery, construction and rover work require a surface. Saved plans remain available for editing and active flights are not migrated. Plans can retain an optional stable preview zone; missing or unrecognised zones use the original prime location. The visual fixture can compare four equatorial preview locations, and the landing sequence passes a plan's zone to orbital, surface and observed-imagery sampling. The existing mining division grid still uses a separate biome model, and generated and authored contracts do not yet persist a shared zone. A complete migration needs a location selection and identity across all mission types and a playable field driven by that same terrain.

With the preview flag enabled, a self-planned delivery can now opt into a landing site on supported surface bodies. On arrival it shows the chosen descent and opens the seeded interactive rover delivery field from that same solar patch. The player's mission and cargo remain in Landnam's existing save and settlement flow; pausing the field restarts the local unload interaction, and cargo is settled only after completing it. Standard deliveries and legacy plans retain their existing flow. The field itself is ephemeral, not a persistent world; other mission types are not migrated. The `solar-site-delivery` stage fixture starts at descent for a visual review of the rover unload and return. The full planner-to-launch path and persistent fields still need end-to-end verification before treating this as a finished playtest.

In the enabled `solar-site-delivery` fixture, the Mercury delivery was checked through unloading and return transit. A separate check with the WASM unavailable showed the cargo still on the mission and the retry and pause actions; restoring the asset and retrying opened the field. This fixture starts in descent and does not verify planning, launch, settlement, or a signed-in save. A selected-site field must load the matching solar terrain; it no longer silently substitutes an unrelated legacy field when the generator is unavailable. The legacy rover art and grid are still present in this playable field.

The vendored Takeon engine accepts a categorical surface-material grid alongside a DEM. With the preview flag enabled, read-only and seeded ephemeral fields receive both grids from the same solar patch used by the orbit and landing views. The solar visual fixture can switch to the engine field for inspection. The bundled engine omits planetary image assets to limit its size; the separate solar-preview WASM supplies those assets. Persistent fields still use their existing generator. Before migrating them, save a generator identity and pin the matching engine and data version so a field always resumes with the same generator even when settings or assets change.

The major moon catalog now includes the Moon, Phobos and Deimos, Jupiter's four Galilean moons, Saturn's Mimas, Enceladus, Tethys, Dione, Rhea, Titan and Iapetus, Uranus's Miranda, Ariel, Umbriel, Titania and Oberon, and Neptune's Triton. The latter ten Saturnian and Uranian additions need a solar-preview WASM rebuilt from the corresponding Takeon checkout; an older deployed WASM cannot generate them. Their temperatures and broad surface categories guide stylised seeded profiles, not measured topography. Descent-preview rocks and ice details are deterministic per site and biome, and are not placed on ocean or methane lakes. These details are visual only; they are not yet shared objects in persistent gameplay or mining.

With the preview enabled, a self-planned mining mission can also select a site. Its existing laser scene uses the selected patch's centre biome colour and a site-specific landscape arrangement; ore selection, cargo, charges and settlement remain in the existing mining system. This is a stylised cross-section, not the Takeon field or a persistent, depletable deposit. The `solar-site-mining` fixture starts with one iron and 12 charges to review the scene and resumption HUD. If the generator cannot load, the field offers a retry instead of silently showing another site.

Existing marked solar snapshots are checked against both destination and requested zone before restoration. The sync adapter refuses to load a remote field while its own snapshot is queued for upload. For signed-in players it also refuses to substitute an unscoped local field when the server cannot be reached, waits for offline queue writes, and queues later saves behind a pending snapshot. New offline saves queue the world and its complete structure set together, and replay structure removals before the field can be loaded. The server writes are still separate, not transactional. Persistent solar-field creation remains disabled: safe reconciliation across offline edits, multiple devices, concurrent saves and structure records still needs implementation and testing. Legacy field snapshots must continue to load unchanged. Mining deposits and edits are not yet saved into those fields.

Landnam's surface climate profiles for the newer moons now use the same broad temperature and roughness inputs as their Takeon profiles, while retaining their existing biome family ids. The landing bridge rejects a response if the patch's centre does not match the orbital centre sample. Coverage checks include every catalogued solid destination and every solid biome currently emitted by Takeon; these checks do not replace an end-to-end test of the flagged preview, deployment assets, or saved playable fields.
